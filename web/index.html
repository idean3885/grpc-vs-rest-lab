gRPC vs REST 브라우저 관측

개발자도구를 열고(Cmd+Option+I) Network 탭을 띄운 뒤 아래 버튼을 누른다. 같은 데이터를 다섯 가지 방식으로 요청하므로 Size·Time·Content-Type 을 나란히 비교할 수 있다. 아래 표는 데브툴 목록과 같은 순서로 쌓인다. 데브툴에서 Name 열 헤더를 우클릭해 Method 를 체크하면 GET·POST·OPTIONS 가 열로 표시되어 대조가 쉽다.

# 방식 요청 전송 계층 Content-Type 본문 바이트 건당 소요 본문 앞부분

1번과 2번을 비교한다. 2번은 서버가 gRPC·프로토버프로 통신한 결과인데 데브툴에는 JSON 으로 보인다. 게이트웨이 경유임을 구별할 단서는 응답 헤더의 Grpc-Metadata-Content-Type: application/grpc 뿐이다. 즉 grpc-gateway 를 쓰면 브라우저 쪽은 그냥 REST 다.

3번이 프로토버프의 실제 모습이다. Response 탭에 바이너리가 나타난다. 4번은 같은 바이트를 base64 로 감싼 것이라 눈으로 읽기 쉽다. 두 방식 모두 브라우저가 프로토버프 프레임을 직접 주고받는다.

브라우저가 순수 gRPC 를 쓸 수 없는 이유는 gRPC 가 호출 상태를 HTTP/2 trailer 에 담는데 fetch 가 trailer 를 읽을 수 없기 때문이다. grpc-web 은 그 상태를 본문 끝의 trailer 프레임(0x80)으로 옮겨 해결한다.

데브툴에 OPTIONS 요청이 섞여 보인다. 위 표에는 나타나지 않는 프리플라이트다. 1·2번 GET 은 단순 요청(simple request)이라 프리플라이트가 없지만, grpc-web 은 Content-Type: application/grpc-web+proto 가 단순 요청 허용 목록 밖이고 X-Grpc-Web 이 커스텀 헤더라 브라우저가 OPTIONS 를 먼저 보낸다. 즉 크로스 오리진에서 grpc-web 을 쓰면 프로토버프 크기 이득과 별개로 OPTIONS 왕복 비용이 붙는다. Access-Control-Max-Age 로 캐시 기간을 늘려 완화하며, 같은 오리진에 두면 애초에 발생하지 않는다.
