# 벤치마크 도구와 지표

프로토콜 비교는 **지표 하나로 판정할 수 없다.** 처리량만 보면 결론이 뒤집히고, 지연만 보면 대규모에서 먼저 터지는 축을 놓친다. 이 디렉토리는 무엇을 어떤 도구로 재고 어떻게 읽어야 하는지를 정리한 것이다.

측정 설계와 통제 항목은 [../docs/benchmark-design.md](../docs/benchmark-design.md), 결과 요약은 [../README.md](../README.md).

## 왜 두 지점에서 재는가

| 측정 | 대상 | 무엇을 보는가 |
|------|------|-------------|
| 직접 | 프로토콜을 바로 때린다 (`:8081` REST, `:9090` gRPC) | 프로토콜 자체의 상한 |
| **경유** | 애플리케이션을 거친다 (`:8080` identity-server) | **실제 코드를 통과한 차이** |

직접 측정만 하면 부하 도구의 클라이언트 구현이 결과를 지배할 수 있다. 실제로 k6 의 gRPC 클라이언트는 리플렉션으로 받은 스키마로 프로토버프를 동적 파싱해 JS 객체로 바꾸는데, 그 비용이 gRPC 쪽에만 얹혀 **gRPC 가 3.3배 느리다는 잘못된 결론**이 나온다.

경유 측정은 호출 측(`identity-server`)이 두 방식으로 상류를 부르고 k6 는 얇은 요약 응답만 받는다. 도구 측 파싱 비용이 양쪽에 동일하게 걸리므로 이쪽 값을 신뢰한다.

## 도구

| 도구 | 재는 것 | 왜 이 도구인가 |
|------|--------|--------------|
| **k6** v1.7+ | 처리량, 지연 백분위, 전송량, 오류율 | REST 와 gRPC 를 **같은 러너**로 잴 수 있다 (`k6/net/grpc` 코어 모듈). 도구가 달라 생기는 차이를 제거 |
| **lsof** | TCP 커넥션 수 | k6 로는 보이지 않는 축. 대규모에서 지연보다 먼저 병목이 된다 |
| **jcmd** `Thread.print` | 스레드 그룹별 개수 | 동시성 모델 차이(스레드 풀 대 이벤트 루프 대 가상 스레드 캐리어)를 드러낸다. 가상 스레드 자체는 여기 안 나온다 |
| **ps** `-o time` | 프로세스 누적 CPU 시간 | 처리량이 다르므로 **요청당 CPU** 로 정규화해야 비교가 성립 |
| **curl** `-w '%{size_download}'` | 응답 본문 크기 | 직렬화 크기를 단건으로 확인 |

## 봐야 하는 지표 세트

여섯 개를 함께 본다. 하나만 보면 오해가 생기는 이유를 함께 적었다.

| 지표 | 단위 | 하나만 보면 생기는 오해 |
|------|------|---------------------|
| 처리량 (RPS) | req/s | 지연이 무너진 상태로도 높게 나올 수 있다 |
| 지연 백분위 | p50·p95·p99 | 평균만 보면 꼬리를 놓친다. 팬아웃 환경에서는 꼬리가 사용자 경험을 지배 |
| **꼬리 지연** | max·p99.9 | p95 가 2배 차이일 때 max 는 6.6배까지 벌어졌다 (실측) |
| 전송량 | 바이트/req | 지연 이득이 없는 구간에서도 대역폭 비용은 남는다 |
| **TCP 커넥션 수** | 개 | 지연·처리량에 안 나타나지만 파일 디스크립터·메모리 한계에 직접 걸린다 |
| **요청당 CPU** | µs/req | 총 CPU 만 보면 처리량 차이에 가려진다. 반드시 정규화 |
| 오류율 | % | 나머지 지표가 전부 무의미해지는 전제 조건 |

`RPS`(requests per second)가 HTTP·API 의 표준 표기다. `TPS`(transactions per second)는 트랜잭션 정의가 도메인마다 달라 API 비교에는 덜 쓴다.

## 실행

```bash
# 1회차: REST 플랫폼 스레드 (기본)
VIRTUAL_THREADS=false ../run-all.sh
./measure.sh rest 1        # → results/rest-size1.*
./measure.sh rest 1000
./measure.sh grpc 1
./measure.sh grpc 1000

# 2회차: REST 가상 스레드. 서버를 새로 띄워야 스레드 풀 오염이 섞이지 않는다
../stop-all.sh
VIRTUAL_THREADS=true ../run-all.sh
./measure.sh rest 1        # → results/rest-vt-size1.*
./measure.sh rest 1000

# 처리량·지연만 여러 크기로 훑기
./run.sh service     # 경유 측정 (애플리케이션을 거친다)
./run.sh direct      # 직접 측정 (프로토콜을 바로 때린다)
```

`measure.sh` 는 워밍업을 본 측정과 분리하고, 부하가 정상 상태에 이른 뒤 커넥션·스레드를 스냅샷하며, 부하 구간에서 소비한 CPU 시간을 계산한다.

환경 변수로 조절한다.

```bash
VUS=200 DURATION=60s ./measure.sh grpc 100
```

## 결과 해석 가이드

### 요청당 CPU 로 정규화한다

총 CPU 시간을 그대로 비교하면 처리량 차이에 가려진다.

```
요청당 CPU = 부하 구간 CPU 소비(초) / 처리한 요청 수 × 1,000,000  (µs/req)
```

실측 예시다. 총 CPU 만 보면 gRPC 가 적게 쓰는 것처럼 보이지만, 정규화해야 실제 차이가 나온다.

| | 총 CPU | 요청 수 | **요청당 CPU** |
|---|---|---|---|
| REST 플랫폼 size=1 | 54.15 s | 810,951 | 66.8 µs |
| REST 가상 size=1 | 56.06 s | 934,174 | **60.0 µs** |
| gRPC size=1 | 44.32 s | 711,720 | 62.3 µs |
| REST 플랫폼 size=1000 | 88.08 s | 244,609 | 360.0 µs |
| REST 가상 size=1000 | 81.98 s | 242,583 | 337.9 µs |
| gRPC size=1000 | 77.45 s | 380,614 | **203.5 µs** |

단건에서는 **가상 스레드 REST 가 gRPC 보다 CPU 를 덜 쓴다.** 페이로드가 커지면 직렬화 비용 차이가 지배해 gRPC 가 40% 적게 쓴다.

### 스레드는 모드에 따라 세는 대상이 다르다

가상 스레드는 `jcmd Thread.print` 에 나오지 않는다. 플랫폼 스레드만 보이므로, 가상 스레드 모드에서는 **캐리어(`ForkJoinPool-1-worker`)** 를 센다.

| 모드 | 요청 처리 스레드 | 동시성 증가 시 |
|------|----------------|--------------|
| 플랫폼 | `http-nio-8081-exec-N` 38~50개 | 비례해서 늘어난다 |
| 가상 | `ForkJoinPool-1-worker-N` 12개 | **고정** |

`measure.sh` 는 `http-nio-<port>-exec-` 유무로 모드를 판정해 결과 파일명에 반영한다(`rest` 대 `rest-vt`). `Acceptor` 와 `Poller` 는 두 모드 모두 플랫폼 스레드로 남으므로 판정 기준에서 제외한다. 라벨을 손으로 붙이지 않는 이유는 회차를 섞는 사고를 막기 위해서다.

### 커넥션은 실제 수로 환산한다

`lsof` 는 **클라이언트측 소켓과 서버측 소켓을 각각 센다.** 같은 커넥션이 두 줄로 나온다.

```
java 5914  (클라이언트)  127.0.0.1:49799 -> 127.0.0.1:9090
java 58302 (서버)        127.0.0.1:9090  -> 127.0.0.1:49799
```

`measure.sh` 는 2로 나눠 실제 커넥션 수를 낸다. 직접 셀 때는 이 점을 감안해야 한다.

## 함정 목록

측정을 무효로 만드는 것들이다. 순서대로 확인한다.

**1. 워밍업을 빼면 결론이 뒤집힌다.** JVM 첫 호출은 클래스 로딩과 JIT 미적용 상태다. 첫 호출만 보면 gRPC 가 REST 의 3배 느리게 나온다(173 ms 대 58 ms). `measure.sh` 는 워밍업을 별도 실행한다.

**2. 커넥션 재사용을 양쪽에 대칭으로 맞춘다.** gRPC 채널은 커넥션을 유지하는데 REST 풀을 잡지 않으면 REST 에만 TCP 핸드셰이크 비용이 반복 계상된다. 반대로 부하 도구에서 가상 사용자마다 gRPC 채널을 새로 만들면 gRPC 가 불리해진다. `k6/grpc.js` 는 `__ITER === 0` 에서만 `connect()` 한다.

**3. 응답을 실제로 파싱한다.** `discardResponseBodies` 를 켜면 역직렬화 비용이 측정에서 빠진다. 다만 그 상태와 켠 상태를 **둘 다** 재면 도구 측 비용을 분리할 수 있다.

**4. 스레드 풀은 부하 후에도 유지된다. 실측 왜곡 12%.** 앞선 REST 부하가 늘려놓은 스레드가 남은 JVM 에서 gRPC 1,000건을 재면 11,317 req/s, 새 JVM 에서 재면 12,685 req/s 였다. 회차를 섞으면 이만큼 틀린다. 축을 바꿀 때는 서버를 다시 띄운다.

**5. 도구의 클라이언트 구현을 의심한다.** 위 "왜 두 지점에서 재는가" 참조.

**6. 기준선을 정지된 것으로 두지 않는다.** REST 를 플랫폼 스레드로만 두고 비교하면 gRPC 단건 열세가 0.88배로 보이지만, 가상 스레드 기준선에서는 0.76배다. 비교 대상도 개선되므로 "무엇 대비" 를 항상 밝힌다.

**7. 가상 스레드 모드를 라벨로 신뢰하지 않는다.** 서버가 실제로 어느 모드로 떴는지 스레드 덤프로 판정한다. `measure.sh` 가 자동으로 하고, 결과 파일명에 반영한다.

## 측정 한계

수치를 인용할 때 함께 밝혀야 한다.

- **단일 호스트.** 왕복 지연이 거의 0이라 HTTP/2 다중화 이득이 나타나지 않는다. 즉 **gRPC 에 불리한 조건**이고, 실제 네트워크에서는 교차점이 더 작은 페이로드 쪽으로 이동할 것으로 예상하되 검증하지 않았다.
- **DB 없음.** 인메모리 조회로 고정했으므로 값은 프로토콜 오버헤드의 **상한**이다.
- **동시성 모델을 부분적으로만 통제했다.** REST 를 플랫폼·가상 두 축으로 재긴 했지만 gRPC-java 는 여전히 Netty 이벤트 루프 + 별도 executor 다. 세 축이 같은 서버 런타임을 공유하지 않는다.
- **가상 스레드 개별 수를 세지 못했다.** 플랫폼 스레드 덤프에 나오지 않고 순간 표본으로 안정적으로 잡히지 않아 캐리어 수만 보고한다.
- **호출 측은 플랫폼 스레드로 고정했다.** `identity-server` 에 켜면 두 프로토콜에 똑같이 걸려 축이 흐려진다. 이 랩이 다루는 것은 상류 서버의 스레드 모델뿐이다.
- **클라이언트 측 CPU 미측정.** `profile-server` 만 쟀고 호출 측 직렬화 비용은 빠져 있다.
- **꼬리 지연 표본 부족.** p95 까지만 신뢰한다. p99.9 를 말하려면 더 긴 부하가 필요하다.
- **지연의 HTTP/2 기여분 미분리.** 크기 축은 게이트웨이 대조(전송 동일·직렬화만 다름)로 분리됐고, 남은 것은 지연 쪽이다. 가르려면 REST 를 h2c 로도 재야 한다.
