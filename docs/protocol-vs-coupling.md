# 프로토콜을 바꾸는 것과 결합을 바꾸는 것

gRPC 도입을 검토하면서 자주 섞이는 두 질문이 있다.

1. 서비스 간 통신을 무엇으로 주고받을까 (JSON / 프로토버프)
2. 서비스 간 결합을 어떻게 둘까 (동기 호출 / 비동기 메시지)

**두 질문은 독립이다.** gRPC 는 1번만 바꾼다. 그런데 "gRPC 로 바꾸면 서비스 간 결합이 정리된다"는 기대가 자주 붙고, 그 기대는 성립하지 않는다.

## 두 축은 직교한다

|  | 동기 (의존 방향이 생긴다) | 비동기 (의존이 역전된다) |
|---|---|---|
| **JSON·텍스트** | REST | 이벤트 (JSON 페이로드) |
| **프로토버프** | **gRPC** | 이벤트 (proto 스키마 페이로드) |

가로축은 직렬화와 전송 계층이다. 지연·전송량·계약 검증 시점이 여기서 결정된다. 측정값은 [benchmark-design.md](benchmark-design.md) 에 있다.

세로축은 결합 방향이다. 누가 누구를 아는지가 여기서 결정된다.

gRPC 는 왼쪽 아래에서 왼쪽 위로 가는 이동이다. **세로축 위치는 그대로다.**

## gRPC 로 이벤트를 대체할 수 없는 이유

gRPC 는 동기 RPC 다. 호출하는 쪽이 호출받는 쪽의 서비스 이름·메서드·주소를 알아야 한다. 이 랩의 코드에도 그대로 드러난다.

```java
// identity 가 profile 을 안다. 스텁 타입 자체가 상대를 지시한다.
private final ProfileServiceGrpc.ProfileServiceBlockingStub profileStub;
```

이벤트는 반대다. 발행자는 소비자를 모른다.

```java
// 누가 받는지 발행부에 없다. 그래서 발행자는 소비자에 의존하지 않는다.
eventPublisher.publish(new ProfileUpdatedEvent(userId));
```

**순환 의존을 끊는 힘은 프로토버프가 아니라 이 성질에서 나온다.** A→B 는 동기 호출, B→A 는 이벤트로 두면 의존 방향이 A→B 한 방향만 남는다. 여기서 이벤트 쪽을 gRPC 로 바꾸면 B 가 A 를 알아야 하므로 **순환이 즉시 복귀한다.**

gRPC 에 스트리밍이 있지만 방향을 뒤집지는 못한다. 양방향 스트리밍도 스트림을 여는 쪽이 상대를 알아야 시작된다.

그래서 실무 스택에서 gRPC 와 메시지 브로커가 함께 등장하는 것은 중복이 아니다. 서로 다른 축을 담당한다.

## 사례: 이벤트 일변도의 대가

이전에 참여한 플랫폼 서비스에서 겪은 구조다. 회사·제품 식별 정보는 제외하고 구조만 적는다.

**출발 상태.** 모듈이 여러 개인 MSA 였고, 서비스 간 통신을 **메시지 이벤트로만** 처리했다. 동기 호출 클라이언트가 아예 없었다. 결합도 관점에서는 이상적인 상태로 보인다. 모든 모듈이 서로를 모른다.

**드러난 문제.** 결합은 느슨했지만 **호출 흐름이 코드에 남지 않았다.** 어떤 요청이 어느 모듈을 거쳐 무엇을 바꾸는지 추적하려면 발행부와 구독부를 전부 훑어야 했다. 이벤트가 늘어나면서 모듈 역할과 경계도 흐려졌고, 흐름을 재현하기 어려워 테스트도 어려웠다.

**전환.** 포트·어댑터로 외부 의존을 분리하고 도메인 모듈을 응집하면서, 과도한 이벤트 의존을 **명시적 호출로 정리**했다. 방향에 주의할 필요가 있다. 이벤트를 도입해 결합을 줄인 것이 아니라, **이벤트만 쓰던 구조에서 흐름을 드러내기 위해 동기 호출을 되살린 것**이다.

**되살리자 드러난 것.** 명시적 호출을 넣으니 **모듈 빌드 의존 순환**이 생겼다. 런타임 의존성 주입은 동작했기 때문에 실행은 됐지만, 클라이언트 모듈을 빌드할 때 잘못 빌드되고 실행 시점에 내부 의존이 엉키는 문제가 반복됐다. 의존 방향을 정리해 **선형(비순환) 구조**로 해소했다.

**트레이드오프.** 명시적 호출은 결합도를 올린다. 그 시점에는 흐름 가시성이 결합도보다 큰 문제였기 때문에 그쪽을 택한 것이고, 순환은 의존 방향 정리로 관리했다. 결과로 흐름과 모듈 역할이 드러나고 도메인 로직이 외부 의존과 분리되어 단위 테스트 범위가 넓어졌다.

여기서 얻는 것은 "이벤트가 나쁘다"가 아니다. **느슨한 결합의 대가가 흐름 불투명이라는 점, 그리고 그 대가를 지불할 값어치가 있는지는 그때의 병목이 무엇인지에 달렸다는 점**이다.

## 명시적 호출이 빌드 의존을 만드는 지점

위 사례에서 순환이 생긴 원인을 코드 수준으로 따라가면 이렇다.

동기 호출 클라이언트를 두려면 **요청·응답 타입**이 필요하다. 그 타입을 도메인 타입으로 쓰면 클라이언트를 담은 모듈이 도메인 모듈에 의존한다. 양쪽 모듈이 서로를 호출하면 그 의존이 마주 보게 되고, 빌드 그래프에 순환이 생긴다.

```
A-domain ──▶ B-client ──▶ B-domain ──▶ A-client ──▶ A-domain
   ▲                                                    │
   └────────────────────────────────────────────────────┘
```

런타임에는 스프링이 빈을 주입하니 동작한다. 깨지는 것은 빌드 순서와 클래스패스다.

## gRPC 의 proto 모듈이 주는 답

이 랩은 그 지점을 의도적으로 다르게 구성했다. 계약이 Java 인터페이스가 아니라 **`.proto` 스키마**에 있다.

```
identity ──┐
           ├──▶ proto  (.proto + 생성 스텁)
profile  ──┘
```

`proto` 모듈은 **아무것도 의존하지 않는다.** 도메인 타입을 모르고, 스키마에서 생성된 독립 타입만 담는다. 양쪽이 이 모듈에만 의존하므로 방향이 마주 볼 수 없고, 빌드 그래프가 비순환으로 유지된다.

`identity` 가 `profile` 에 컴파일 의존하지 않는다는 것이 이 구성의 확인 지점이다. `settings.gradle` 과 각 모듈 `build.gradle` 에서 그 의존이 없음을 볼 수 있다.

REST 로 같은 성질을 얻으려면 클라이언트 인터페이스와 DTO 를 도메인과 분리된 계약 모듈에 두고, 그 모듈이 도메인을 참조하지 않도록 규율을 지켜야 한다. 가능하지만 **지켜야 하는 규율이고, 어기기 쉽다.** proto 는 도구가 그 분리를 강제한다. 스키마 파일에는 애초에 도메인 타입을 쓸 방법이 없다.

**대가도 있다.** 도메인 타입과 proto 타입 사이 매핑 코드가 필요하다. 이 랩에서는 `ProfileProtoMapper`, `ProfileMapper` 가 그 비용이다. 타입이 두 벌이 되고 필드를 추가할 때 양쪽을 손대야 한다. 규모가 작으면 이 비용이 이득보다 클 수 있다.

## 선택 기준

| 상황 | 선택 | 근거 |
|------|------|------|
| 흐름 추적이 병목 | 동기 호출 (REST 또는 gRPC) | 호출 관계가 코드에 남는다 |
| 순환 의존이 병목 | 한 방향을 이벤트로 | 발행자가 소비자를 모른다 |
| 다건·대용량 내부 호출이 많다 | gRPC | 1,000건에서 처리량 1.43배 |
| 단건 조회가 대부분 | REST 유지 | gRPC 가 오히려 0.79배 |
| 대역폭·트래픽 비용이 병목 | gRPC | 크기 무관 2.5배 절감 |
| 서비스 수가 늘어 계약 사고가 잦다 | gRPC | 재생성 시 컴파일 단계에서 드러난다 |
| 모듈 간 빌드 의존이 엉킨다 | gRPC 의 스키마 모듈 분리 | 계약 모듈이 도메인을 참조할 수 없다 |

마지막 두 줄이 성능과 무관한 채택 근거다. 그리고 실무에서 더 자주 문제가 되는 쪽이기도 하다.

## 정리

프로토콜 교체로 해결되는 문제와 결합 방향 재설계로 해결되는 문제는 다르다.

- **gRPC 가 해결하는 것**: 전송량, 다건 구간 지연, 계약 검증 시점, 계약 모듈의 의존 분리
- **gRPC 가 해결하지 않는 것**: 순환 의존, 서비스 간 시간 결합, 장애 전파

순환 의존과 시간 결합은 비동기 메시징의 영역이다. 두 축을 섞어 "gRPC 를 넣으면 아키텍처가 정리된다"고 기대하면, 프로토콜을 바꾸고도 같은 문제가 남는다.
