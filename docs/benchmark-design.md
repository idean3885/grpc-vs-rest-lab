# 벤치마크 설계

## 측정하려는 것

"gRPC 가 REST 보다 빠른가"는 답할 수 없는 질문이다. 조건에 따라 답이 뒤집힌다. 그래서 질문을 나눈다.

1. 어떤 조건에서 차이가 커지고, 어떤 조건에서 사라지는가
2. 차이의 원인이 무엇인가 (직렬화 · HTTP/2 · 커넥션 재사용)
3. grpc-gateway 를 끼우면 얻은 이득을 얼마나 반납하는가

## 측정 축

| 축 | 값 |
|----|----|
| 전송 방식 | REST/JSON (HTTP/1.1) · gRPC unary (HTTP/2) · gRPC server streaming · grpc-gateway 경유 |
| 페이로드 | 1건 · 100건 · 1,000건 · 10,000건 |
| 동시성 | 1 · 50 · 200 |
| 지표 | p50 · p95 · p99 지연 · RPS · 요청당 전송 바이트 |

페이로드 크기를 네 단계로 나누는 이유는, 직렬화 비용이 크기에 비례해 커지는 반면 커넥션·헤더 오버헤드는 크기와 무관하게 고정이기 때문이다. 두 성분의 비율이 크기에 따라 뒤바뀌므로 단일 크기 측정으로는 원인을 분리할 수 없다.

## 통제 항목

측정을 무효로 만드는 요인들과 각각의 처리.

### 1. 커넥션 재사용 비대칭

gRPC 채널은 커넥션을 유지하고 HTTP/2 스트림으로 요청을 멀티플렉싱한다. REST 쪽 keep-alive 를 끄거나 커넥션 풀을 잡지 않으면, REST 에만 TCP 핸드셰이크 비용이 요청마다 계상된다. 그 상태의 측정값은 "프로토콜 차이"가 아니라 "설정을 덜 한 REST" 다.

처리.

- 서버: `server.tomcat.max-keep-alive-requests: -1`, `keep-alive-timeout: 60s`
- 클라이언트: Apache HttpClient5 `PoolingHttpClientConnectionManager` 를 명시하고 `maxConnTotal`·`maxConnPerRoute` 를 톰캣 워커 수와 맞춤
- 반대 방향도 주의. 부하 도구에서 가상 사용자마다 gRPC 채널을 새로 만들면 gRPC 가 불리해진다. k6 스크립트에서 채널 연결을 `init` 단계로 올린다.

### 2. JVM 워밍업

첫 호출은 클래스 로딩과 JIT 미적용 상태다. 이 랩의 첫 관측이 그 영향을 그대로 보여준다.

| 호출 순서 | size | REST | gRPC |
|-----------|------|------|------|
| 첫 호출 | 1 | 58.1 ms | **173.3 ms** |
| 두 번째 | 100 | 6.6 ms | 4.1 ms |
| 세 번째 | 1,000 | 7.7 ms | 7.2 ms |

첫 호출만 보면 gRPC 가 REST 보다 3 배 느리다. 채널 최초 연결과 프로토버프 관련 클래스 로딩이 한 번에 발생하기 때문이다. 워밍업 없이 측정한 벤치마크가 "gRPC 가 더 느리다"고 보고하는 사례의 상당수가 이 구간을 측정한 결과로 보인다.

처리: 각 측정 전 워밍업 구간을 두고, 그 구간 결과를 집계에서 제외한다.

### 3. 도메인 로직 차이

프로토콜별로 서버를 따로 만들면 로직이 두 벌이 되어, 측정된 차이가 프로토콜 차이인지 구현 차이인지 알 수 없다.

처리: 두 인바운드 어댑터가 같은 UseCase 하나를 호출한다. 프로토콜별 분기 코드가 없다. [architecture.md](architecture.md) 참조.

### 4. JVM 상태 차이

서버를 각각 띄워 비교하면 워밍업 정도·GC 시점·힙 점유가 서로 다르다.

처리: 두 전송을 한 프로세스의 다른 경로(`/me/rest`, `/me/grpc`)로 노출해 같은 JVM 에서 번갈아 측정한다.

### 5. DB 지연

DB 왕복이 수 밀리초면 프로토콜 오버헤드 차이는 그 안에 묻힌다.

처리: 인메모리 조회로 고정(10,000건 사전 생성). **따라서 이 랩의 수치는 프로토콜 오버헤드의 상한이다.** 실제 서비스에서는 DB·외부 API 지연이 지배적이므로 프로토콜 교체 효과가 이보다 작게 나타난다. 이 한계를 결론에 명시한다.

### 6. 측정 구간 오염

응답에 프로필 원본을 담으면, 클라이언트 to identity 구간의 JSON 직렬화 비용이 측정 대상인 identity to profile 구간보다 커질 수 있다.

처리: 응답에 건수·표본 닉네임·상류 왕복 시간만 담는다. 표본 닉네임을 포함시키는 이유는 응답 본문이 실제로 역직렬화됐음을 확인해 최적화로 생략되지 않게 하기 위해서다.

### 7. TLS

TLS 핸드셰이크와 암복호화 비용이 프로토콜 차이에 섞인다.

처리: 양쪽 모두 평문. 실제 운영에서는 서비스 메시가 mTLS 를 담당하는 구성이 흔하므로, 이 랩의 값에 TLS 비용을 별도로 더해 해석해야 한다.

## 측정 방법

재는 지점을 둘로 나눈다.

### 직접 측정: 프로토콜을 바로 때린다

프로토콜 자체의 처리량과 지연을 본다. k6 는 v0.49 부터 `k6/net/grpc` 코어 모듈로 unary·스트리밍을 지원하므로, REST 와 gRPC 를 같은 러너·같은 부하 모델로 측정할 수 있다. 도구가 달라 생기는 차이를 제거하는 것이 목적이다.

대상.

- `GET :8081/v1/profiles?size=N` (REST 직접)
- `profile.v1.ProfileService/ListProfiles` (gRPC 직접)
- `GET :8090/v1/profiles?size=N` (grpc-gateway 경유)

### 경유 측정: 애플리케이션을 거친다

실제 코드 형태 그대로 비교한다. `identity-server` 가 `RestClient` 선언형 인터페이스와 gRPC 스텁으로 각각 호출하고, 상류 왕복 시간을 응답에 담아 보고한다.

- `GET :8080/api/v1/me/rest?size=N`
- `GET :8080/api/v1/me/grpc?size=N`

직접 측정이 프로토콜의 이론적 차이를, 경유 측정이 실제 코드를 통과한 차이를 보여준다. 두 값의 간격이 프레임워크 오버헤드다.

### 전송 바이트 측정

지연과 별개로 요청당 실제 전송량을 비교한다. 같은 데이터를 JSON 과 프로토버프로 직렬화했을 때의 크기 차이가 대역폭 비용과 직결된다.

- REST: 응답 `Content-Length`
- gRPC: 메시지 직렬화 크기 + 5 바이트 프레임 헤더
- 브라우저 데브툴 Size 열 대조

## 알려진 한계

수치를 인용할 때 함께 밝혀야 하는 조건들.

- **단일 머신 측정.** 클라이언트와 서버가 같은 호스트에 있어 네트워크 왕복 시간이 0 에 가깝다. RTT 가 큰 환경에서는 HTTP/2 멀티플렉싱 이득이 이 랩보다 크게 나타난다. 즉 이 랩은 gRPC 에 불리한 조건이다.
- **DB 없음.** 위 5번 항목 참조. 프로토콜 오버헤드의 상한값이다.
- **동시성 모델을 부분적으로만 통제했다.** REST 쪽 스레드 모델을 플랫폼·가상 두 축으로 재긴 했지만 gRPC-java 는 여전히 Netty 이벤트 루프 + 별도 executor 다. 세 축 중 어느 것도 같은 서버 런타임을 공유하지 않으므로, 남은 차이에 런타임 차이가 얼마나 섞였는지는 분리하지 못했다.
- **가상 스레드 개별 수를 세지 못했다.** 가상 스레드는 `jcmd Thread.print` 에 나오지 않고, `Thread.dump_to_file` 로도 순간 표본에서는 부하 중 개수를 안정적으로 잡을 수 없었다. 캐리어 스레드 수만 보고한다.
- **호출 측 스레드 모델은 상수다.** `identity-server` 에 가상 스레드를 켜면 REST 와 gRPC 두 경로에 똑같이 걸려 축이 흐려지므로 플랫폼으로 고정했다. 이 랩이 다루는 것은 상류 서버의 스레드 모델뿐이다.
- **가상 스레드 기준선의 교차점을 재지 않았다.** 단건 열세가 0.88배에서 0.76배로 커졌으므로 교차점도 이동했을 것이나, 크기별 곡선을 3축으로 다시 재지는 않았다.
- **클라이언트 측 CPU 미측정.** `profile-server` 만 측정했고 호출 측(`identity-server`)의 직렬화 비용은 빠져 있다.
- **JMH 미사용.** 인프로세스 마이크로벤치마크가 아니라 부하 도구 기반 측정이다. 나노초 단위 직렬화 비용을 분리하려면 JMH 가 필요하다.
- **꼬리 지연 표본 부족.** p95 까지만 신뢰한다. p99.9 를 말하려면 훨씬 긴 부하가 필요하다.
- **커넥션 예산 회차의 풀 크기는 인위적이다.** 커넥션 1개는 실무 설정이 아니다. 이 회차가 내는 값은 "커넥션 1개가 나르는 양"이고, 옮겨 쓸 수 있는 숫자는 절대 처리량이 아니라 **배수**(같은 처리량에 REST 커넥션 4개 대 gRPC 1개)다. "REST 는 몇 req/s 에서 무너진다"는 말은 이 회차로 할 수 없다.
- **gRPC 쪽 상한은 찾지 못했다.** 12,800 req/s 구간에서 `profile-server` CPU 가 부하 15초 동안 15.7초였다. 코어 하나를 가득 쓰는 수준이라 그 위는 커넥션이 아니라 CPU 에 막힌다. gRPC 커넥션 1개의 다중화 한계는 이 랩에서 재지 못했다.
- **높은 요청률 구간의 버린 요청에는 부하 도구 몫이 섞였다.** k6 와 두 서버가 같은 호스트에서 CPU 를 나눠 쓰므로, 9,600 이상 구간의 `dropped_iterations` 는 서버 포화와 클라이언트 한계가 함께 작용한 값이다. 양쪽에 같은 조건으로 걸리므로 비교에는 쓰되 절대값으로 인용하지 않는다.
- **커넥션 예산 회차는 size=1 만 쟀다.** 응답이 작은 구간, 즉 정본 회차가 gRPC 열세로 판정한 그 구간이다. 큰 응답과 커넥션 고갈이 겹칠 때는 재지 않았다.
- **지연의 HTTP/2 기여분을 분리하지 못했다.** 크기 축은 분리됐다. 전송이 같고 직렬화만 다른 grpc-gateway(JSON) 대 grpc-web(프로토버프) 대조에서 크기 이득이 직렬화에서 나온다는 것이 확인된다. 남은 것은 **지연** 쪽이다. "HTTP/2 덕분인가 프로토버프 덕분인가"를 지연에서 가르려면 REST 를 h2c 로도 재야 하는데, 톰캣 h2c 설정과 부하 도구의 h2c 지원 문제로 축에서 제외했다.

## 결과

측정 환경: Apple Silicon 단일 호스트, **Java 21 (Corretto 21.0.3)**, 클라이언트와 서버 동일 머신(RTT 거의 0). k6 v1.7.1, 50 VU, 워밍업 별도 실행 후 본 측정. 아래 직접 측정과 크기별 곡선은 Java 17 시절 값이고, **인용 정본은 3축 정본 측정**이다.

### 직접 측정 (size=100, 5 VU, 5s)

| 조건 | REST | gRPC | 비고 |
|------|------|------|------|
| 응답 파싱 포함 | 12,763 req/s | 3,903 req/s | gRPC 가 3.3배 느림 |
| 응답 파싱 제외 | 24,664 req/s | 18,151 req/s | 격차 1.36배로 축소 |
| 요청당 수신 | 13.2 KB | 5.3 KB | gRPC 가 2.5배 작음 |

**응답 파싱을 빼면 격차가 3.3배에서 1.36배로 줄어든다.** gRPC 처리량 저하의 대부분이 프로토콜이 아니라 k6 의 동적 프로토버프 역직렬화 비용이었다. k6 는 리플렉션으로 받은 스키마로 메시지를 동적 파싱해 JS 객체로 변환하는데, 100 건 배열에서 이 비용이 크다. REST 쪽 `r.json()` 은 Go 네이티브 JSON 파서를 쓴다.

즉 **부하 도구를 그대로 믿으면 "gRPC 가 3배 느리다"는 결론이 나온다.** 이 값은 서버 성능이 아니라 도구의 클라이언트 구현을 측정한 것이다.

### 경유 측정: 크기별 곡선 (50 VU, 10~15s)

k6 는 identity-server 의 얇은 요약 응답만 받으므로 도구 측 파싱 비용이 양쪽에 동일하게 걸린다. `상류 p95` 는 identity-server 가 자체 측정한 profile-server 왕복 시간이다.

| size | REST 처리량 | gRPC 처리량 | gRPC 배수 | 상류 p95 (REST) | 상류 p95 (gRPC) |
|------|------------|------------|-----------|----------------|----------------|
| 1 | 24,248 req/s | 22,081 req/s | **0.91×** | 1.48 ms | 2.37 ms |
| 100 | 18,747 req/s | 19,967 req/s | 1.07× | 2.11 ms | 2.72 ms |
| 1,000 | 3,555 req/s | 6,492 req/s | 1.83× | 27.0 ms | 12.4 ms |
| 10,000 | 433 req/s | 797 req/s | 1.84× | 262.8 ms | 123.2 ms |

### 정본 측정: 경유 · Java 21 · 3축 (50 VU, 30s, 워밍업 10s 별도)

처리량·지연만으로는 보이지 않는 축을 함께 수집했다. 도구는 `bench/measure.sh` 다.

**REST 를 두 축으로 나눈다.** Java 21 의 가상 스레드를 켠 REST 가 오늘의 현실적 기준선이므로, 플랫폼 스레드 REST 와만 비교하면 gRPC 이득이 부풀려진다. `spring.threads.virtual.enabled` 는 `profile-server` 에만 걸고 호출 측은 플랫폼으로 고정했다. gRPC 경로는 Netty 라 이 플래그에 영향받지 않는다.

| | REST 플랫폼 | REST 가상 | gRPC |
|---|---|---|---|
| 처리량 1건 | 27,030 req/s | **31,136 req/s** | 23,698 req/s |
| 처리량 1,000건 | 8,153 req/s | 8,085 req/s | **12,685 req/s** |
| 상류 p95 1건 | 1.33 ms | **1.18 ms** | 2.48 ms |
| 상류 p95 1,000건 | 8.36 ms | 9.84 ms | **4.96 ms** |
| 상류 max 1건 | 119.4 ms | **35.5 ms** | 125.0 ms |
| 상류 max 1,000건 | 335.7 ms | 239.6 ms | **50.8 ms** |
| **TCP 커넥션** | 50개 | 50개 | **1개** |
| 부하 구간 CPU 1건 | 54.15 s | 56.06 s | 44.32 s |
| 부하 구간 CPU 1,000건 | 88.08 s | 81.98 s | 77.45 s |
| **요청당 CPU 1건** | 66.8 µs | **60.0 µs** | 62.3 µs |
| **요청당 CPU 1,000건** | 360.0 µs | 337.9 µs | **203.5 µs** |
| 요청 처리 스레드 | `http-nio-exec` 38~50개 | **`ForkJoinPool` 캐리어 12개 고정** | `grpc-default-executor` 39~50개 |

배수는 기준선을 무엇으로 잡느냐로 갈린다.

| gRPC 배수 | vs REST 플랫폼 | vs REST 가상 |
|---|---|---|
| 처리량 1건 | 0.88× | **0.76×** |
| 처리량 1,000건 | 1.56× | 1.57× |
| 요청당 CPU 1,000건 | −43.5% | −39.8% |

**단건 열세가 가상 스레드 기준선에서 커진다.** 반대로 1,000건 이득은 기준선과 거의 무관하다. 스레드 모델을 개선해도 직렬화 비용은 줄지 않기 때문이다.

**가상 스레드는 단건에서만 이득이다.** 1건에서 처리량 1.15배, 최대 지연 119.4 ms → 35.5 ms(3.4배). 1,000건에서는 0.99배로 사라진다. 병목이 스레드 모델에서 직렬화 CPU 로 옮겨가면 손댈 곳이 없다.

**캐리어 스레드는 고정이다.** 플랫폼 스레드는 동시성에 비례해 exec 스레드가 늘지만, 가상 스레드는 캐리어 12개(CPU 병렬성)로 고정된다. 처리량이 같은 1,000건 구간에서도 이 축은 유지되므로, 가상 스레드의 값은 처리량보다 **자원 사용 상한**에 있다.

**스레드 풀 오염을 실측했다.** gRPC 1,000건을 앞선 REST 부하가 늘려놓은 스레드가 남은 JVM 에서 재면 11,317 req/s 였고, 캐리어가 고정된 JVM 에서 재면 12,685 req/s 였다. **12% 차이다.** 회차를 섞으면 이만큼 틀린다. 위 표는 후자 값이다.

앞의 크기별 곡선(4개 크기)은 Java 17 · 짧은 부하 · 워밍업 미분리로 잰 초기 측정이다. 회차가 다르므로 배수를 인용하지 않고 교차점 위치를 보는 용도로만 읽는다.

**커넥션 수 (50개 대 1개)** 는 페이로드 크기와 무관하게 일정하다. HTTP/1.1 은 커넥션당 동시 요청이 하나라서 동시 요청 50개에 커넥션 50개가 필요하고, HTTP/2 는 스트림으로 다중화하므로 하나로 처리한다. 이 회차의 지연·처리량 지표에는 나타나지 않는 축이다. **단 커넥션이 여유 있을 때만 그렇다.** 풀이 마르면 지연으로 전환된다. 아래 커넥션 예산 회차에서 그 지점을 쟀다.

`lsof` 는 클라이언트측·서버측 소켓을 각각 세므로 원시 출력은 두 배로 나온다. 위 값은 2로 나눈 실제 커넥션 수다.

**요청당 CPU** 는 페이로드가 커지면서 벌어진다. 단건에서는 가상 스레드 REST(60.0 µs)가 gRPC(62.3 µs)보다 오히려 적게 쓰고, 1,000건에서는 gRPC 가 40% 적게 쓴다. 직렬화 비용 차이가 여기서 드러난다. 총 CPU 만 비교하면 처리량 차이에 가려지므로 반드시 정규화한다.

**꼬리 지연** 격차도 크기에 비례한다. 1,000건에서 p95 는 1.5배 차이인데 max 는 6배다. p95 만으로 판정하면 놓치는 구간이다.

### 커넥션 예산 회차: 커넥션 1개에 무엇이 실리는가 (열린 루프, size=1, 15s)

정본 회차는 커넥션 풀 200 에 동시 요청 50 이었다. 풀이 병목에 한참 못 미쳤으므로 gRPC 다중화의 이득이 나타날 조건이 아니었다. **정본 회차의 "gRPC 는 단건에서 이득이 없다"는 결론은 커넥션이 여유 있는 구간에 한정된 말이다.**

풀 한계에 닿게 하려면 부하를 27,000 req/s 대로 되돌려야 하고, 그러면 커넥션 고갈·CPU 포화·부하 도구 경합 세 가지가 섞여 원인을 가릴 수 없다. 그래서 반대로 갔다. **부하를 올리지 않고 커넥션 예산을 1개로 낮췄다.**

- REST/1.1: 커넥션 1개는 한 번에 요청 1건 (파이프라이닝은 실무에서 쓰지 않는다)
- gRPC/2: 커넥션 1개에 스트림 여러 개를 다중화

같은 커넥션 1개로 각 프로토콜이 얼마를 나르는지를 재는 형태가 된다. 실행 모델도 바꿨다. 닫힌 루프는 서버가 느려지면 부하도 같이 줄어들어 과부하 구간을 보지 못하므로, **요청률을 고정하는 열린 루프**(k6 `constant-arrival-rate`)로 잰다. 도구는 `bench/run-conn.sh`, 집계는 `bench/summarize-conn.sh` 다.

| 요청률 목표 | 풀 | 전송 | 달성 처리량 | 상류 p50 | 상류 p95 | 상류 max | 버린 요청 |
|---|---|---|---|---|---|---|---|
| 1,600 | 1 | REST | 1,591 req/s | 113 µs | 307 µs | 96.1 ms | 130 |
| 1,600 | 1 | gRPC | 1,600 req/s | 119 µs | 216 µs | 18.7 ms | 2 |
| 3,200 | 1 | REST | 3,190 req/s | 79 µs | 954 µs | 35.1 ms | 152 |
| 3,200 | 1 | gRPC | 3,197 req/s | 78 µs | **155 µs** | 25.1 ms | 48 |
| 6,400 | 1 | REST | 6,316 req/s | 72 µs | 1,795 µs | 84.0 ms | 1,259 |
| 6,400 | 1 | gRPC | 6,373 req/s | 79 µs | **245 µs** | 34.7 ms | 402 |
| 9,600 | 1 | REST | 8,812 req/s | **33,394 µs** | 61,987 µs | 208.4 ms | 11,631 |
| 9,600 | 1 | gRPC | 9,494 req/s | **129 µs** | 1,728 µs | 33.2 ms | 1,582 |
| 12,800 | 1 | REST | 9,043 req/s | 40,396 µs | 54,690 µs | 431.2 ms | **56,008** |
| 12,800 | 1 | gRPC | **12,625 req/s** | 156 µs | 3,806 µs | 50.5 ms | 2,615 |
| 12,800 | **4** | REST | 12,328 req/s | 118 µs | 20,862 µs | 271.4 ms | 6,747 |

**1. 커넥션 1개당 REST 상한은 약 9,000 req/s 다.** 12,800 을 목표로 줘도 9,043 에서 멈추고 목표의 44%(56,008 건)를 버린다. 상류 p50 이 72 µs 였으므로 1/0.000113 ≈ 8,850 req/s 라는 산술과 맞는다. gRPC 는 같은 커넥션 1개로 12,625 req/s 를 냈고 아직 커넥션에 막히지 않았다.

**2. 꼬리 지연이 먼저 갈린다.** 3,200~6,400 구간에서 p50 은 양쪽이 거의 같은데(72~79 µs) p95 는 REST 가 7.3배까지 벌어진다. 중앙값만 보면 정상으로 읽히는 구간에서 이미 대기가 시작되고 있다. **평균·중앙값으로 커넥션 포화를 판정할 수 없다.**

**3. 포화 이후에는 지연 차이가 260배가 된다.** 9,600 구간에서 상류 p50 이 REST 33.4 ms 대 gRPC 0.129 ms 다. 같은 일을 하는데 REST 쪽 요청이 커넥션을 얻으려고 줄을 서 있다.

**4. REST 는 커넥션을 늘려 되찾는다.** 풀을 4개로 올리면 12,328 req/s 로 회복하고 p50 도 118 µs 로 정상화된다. **처리량은 회복되지만 꼬리는 남는다.** gRPC 가 커넥션 1개로 낸 p95 3.8 ms 대 REST 커넥션 4개의 20.9 ms 로 5.5배 차이다.

그래서 이 축의 결론은 성능 우열이 아니라 **교환 조건**이다. 같은 처리량을 REST 는 커넥션 4개로, gRPC 는 1개로 낸다. 커넥션이 싼 환경(내부망, 소수 인스턴스)에서는 풀을 키우면 되고, **커넥션이 비싼 환경(팬인 구조에서 상류 인스턴스가 수백 개)에서는 이 배수가 파일 디스크립터·소켓 메모리·로드밸런서 커넥션 한계에 그대로 곱해진다.**

### 스레드 관측

| 스레드 그룹 | 개수 (50 VU) | 역할 |
|------------|-------------|------|
| `grpc-nio-worker-ELG` | **6 (고정)** | Netty 이벤트 루프. I/O 담당 |
| `http-nio-8081-exec` | 50 | Tomcat 요청 처리 (요청당 스레드) |
| `grpc-default-executor` | 37~47 | gRPC 애플리케이션 콜백 실행 |

gRPC-java 는 I/O 만 이벤트 루프가 처리하고 애플리케이션 콜백은 별도 executor 에서 실행한다. 따라서 **스레드 수 자체는 양쪽 다 동시 요청에 비례해 늘어난다.** 차이는 커넥션 수와 I/O 스레드가 고정이라는 점이다.

스레드 풀은 부하가 끝나도 즉시 회수되지 않아 부하를 번갈아 주면 앞선 측정이 섞인다. 순수 분리에는 서버 재시작이 필요하다.

### 직렬화 크기

| | JSON | protobuf |
|---|------|----------|
| 건당 | 133.6 B | 약 54 B |
| 100건 응답 | 13,386 B | 약 5.3 KB (HTTP/2 프레임·헤더 포함) |

프로토버프 값은 k6 수신 바이트를 반복 수로 나눈 근사치이며 프레임 헤더를 포함한다. 순 페이로드는 이보다 작다.

### 해석

**0. 회차를 함께 밝힌다.** 아래 1~3 번 배수는 크기별 곡선(Java 17, 10~15s, 워밍업 미분리)에서 읽은 값이다. **인용 정본은 3축 정본 측정(Java 21)** 이고, 곡선은 교차점 위치를 볼 때만 쓴다. 정본에서는 단건 0.88 배(가상 스레드 기준선 대비 0.76 배), 1,000 건 1.56 배다. 부하를 길게 주고 워밍업을 분리하면 초기 측정의 유리·불리가 줄어든다.

**1. 작은 페이로드에서 gRPC 는 이득이 없다.** 1 건 조회에서 처리량이 REST 의 0.91 배, 상류 지연은 1.6 배다. 스텁 호출·채널·HTTP/2 프레이밍의 고정 비용이 페이로드 절감분보다 크다. 단건 조회가 대부분인 서비스라면 gRPC 전환으로 지연이 줄지 않는다.

**2. 교차점은 100 건 근처, 약 13 KB 페이로드.** 이 지점에서 처리량이 뒤집히기 시작한다.

**3. 1,000 건 이상에서 1.8배로 수렴한다.** 처리량 1.8배, p95 지연 2.1~2.2배 개선. 1,000 건과 10,000 건의 배수가 거의 같으므로, 이 구간에서는 직렬화·전송량이 지배적이고 비율이 안정된다.

**4. 대역폭은 크기와 무관하게 2.5배 차이.** 지연 이득이 없는 단건 구간에서도 전송량 절감은 그대로 유지된다. 트래픽 비용이나 대역폭 제한 환경에서는 이쪽이 채택 근거가 된다.

**5. RTT 0 조건은 gRPC 에 불리하다.** HTTP/2 멀티플렉싱의 이득은 왕복 지연이 있을 때 나타난다. 실제 네트워크에서는 교차점이 더 왼쪽(작은 페이로드)으로 이동할 것으로 예상하지만, 이 랩에서는 검증하지 않았다. 지연 주입 측정은 후속 과제다.

**6-1. "단건에서 이득 없음"에는 조건이 붙는다.** 정본 회차의 단건 열세(0.88배·0.76배)는 **커넥션이 여유 있는 구간**의 값이다. 커넥션 예산 회차에서 풀을 1개로 낮추면 같은 단건 조회에서 방향이 뒤집힌다. 커넥션 1개당 REST 상한이 약 9,000 req/s 인데 gRPC 는 12,625 req/s 를 넘겨서 아직 막히지 않았고, 포화 구간에서는 상류 p50 이 260배 차이가 난다. **즉 크기 축과 커넥션 축은 서로 독립이고, 응답이 작아도 커넥션이 희소하면 gRPC 가 이긴다.**

**6. 가상 스레드는 단건 쪽 교차점을 오른쪽으로 밀어낸다.** 기준선이 좋아지면 gRPC 가 이기기 시작하는 지점이 더 큰 페이로드로 이동한다. 정본 측정에서 단건 배수가 0.88 배에서 0.76 배로 벌어진 것이 그 방향의 근거이고, 3축 크기별 곡선은 아직 재지 않았다.
